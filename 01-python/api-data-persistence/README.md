Sep 10 Project — API Data Persistence
JSON / Files / HTTP Requests  •  Final Daily Deliverable
Objective
Build a small Python application that retrieves structured data from a public HTTP API, validates the HTTP response, converts the returned JSON into Python data, persists that data to a JSON file, and loads the saved data back into the application.
Target engineering flow:
External API
    ↓
HTTP GET request
    ↓
HTTP response validation
    ↓
JSON → Python data
    ↓
JSON file persistence
    ↓
Load JSON file
    ↓
Python data
    ↓
Display useful information
1. API
Use: https://jsonplaceholder.typicode.com/posts
The API returns a collection of posts containing fields such as:
•	userId
•	id
•	title
•	body
2. Functional Requirements
2.1 Fetch Posts
Create a function responsible for retrieving posts from the API. It must:
•	send an HTTP GET request;
•	use a timeout;
•	verify the HTTP response using raise_for_status();
•	convert the JSON response into Python data;
•	return the retrieved data.
fetch_posts()
API → Python data
2.2 Save Posts
Create a separate function responsible for persistence. It must:
•	receive the posts as Python data;
•	save them into posts.json;
•	use UTF-8 encoding;
•	use json.dump();
•	format the JSON with readable indentation.
save_posts(posts)
Python data → posts.json
2.3 Load Posts
Create a function that reads the persisted data. It must:
•	open posts.json;
•	use json.load();
•	convert the stored JSON back into Python data;
•	return the loaded data.
load_posts()
posts.json → Python data
2.4 Application Workflow
Create a main() function that coordinates the application:
fetch posts
↓
save posts
↓
load saved posts
↓
display results
After loading the persisted data, display:
•	total number of posts;
•	ID of the first post;
•	title of the first post.
3. Error Handling
Handle expected HTTP/network failures using:
requests.RequestException
Display a short user-friendly error message instead of crashing because of an expected request failure. Do not use a broad except Exception to hide unrelated programming errors.
4. Design Requirements
Keep the major responsibilities separate:
fetch_posts()
↓
network / API responsibility

save_posts()
↓
write persistence responsibility

load_posts()
↓
read persistence responsibility

main()
↓
application coordination
Avoid putting the complete workflow into one large function.

7. Constraints
•	Use Python.
•	Use the requests library for HTTP communication.
•	Use Python's built-in json module for JSON persistence.
•	Do not use a database.
•	Do not use external frameworks.
•	Do not hard-code the API response.
•	Do not copy the API data manually into the JSON file.
•	posts.json must be generated by the Python application.
8. Definition of Done
☐ The program successfully calls the API.
☐ A timeout is configured.
☐ HTTP errors are checked before processing data.
☐ The API JSON response is converted into Python data.
☐ The data is persisted to posts.json.
☐ The JSON file remains available after the program terminates.
☐ The program can load the saved JSON back into Python.
☐ The total number of posts is displayed.
☐ The first post's ID is displayed.
☐ The first post's title is displayed.
☐ Expected request/network errors are handled.
☐ Fetching, saving, loading, and orchestration have separate responsibilities.
☐ The project runs from start to finish without manually editing posts.json.
