CLEAN DOMAIN MODEL
Job Application — Python Dataclass Project
Roadmap deliverable: Dunder methods + dataclasses → clean domain model
Objective
Build a production-minded Python domain model using dataclasses, type annotations, defaults, validation, invariants, state mutation, and generated data-model behavior. The finished exercise should be suitable for committing to GitHub.
Scope: Python only. Do not use inheritance, databases, JSON persistence, APIs, Pydantic, or pytest in the first implementation.
1. Domain Model Requirements
Create the following dataclass:
@dataclass
class JobApplication:
    # fields only to begin with
    ...
Required fields and contracts:
Field	Type	Default	Rule
company	str	Required	Must be non-blank
role	str	Required	Must be non-blank
status	str	"applied"	Must be one of the allowed statuses
notes	list[str]	Fresh empty list	Each instance must own its own list
Allowed statuses: applied, interview, rejected, offer
2. Establish Valid Initial State with __post_init__
Use __post_init__ to normalize input and enforce construction-time invariants.
Normalization
•	Strip leading and trailing whitespace from company.
•	Strip leading and trailing whitespace from role.
•	Strip whitespace from status and normalize it to lowercase.
"  OpenAI  "  →  "OpenAI"
"  INTERVIEW  "  →  "interview"
Validation
•	Blank company must raise ValueError.
•	Blank role must raise ValueError.
•	Unsupported status must raise ValueError.
•	Use clear exception messages that describe the violated rule.
Construction contract
If JobApplication(...) returns successfully, the object should begin life in a valid state: non-blank company, non-blank role, and a supported status.
3. Implement change_status(new_status)
Create an instance method that controls status mutation instead of relying on callers to perform validation themselves.
•	Normalize the incoming status.
•	Validate it against the allowed status set.
•	Raise ValueError for an unsupported status.
•	Otherwise update self.status.
job.change_status("interview")
# expected state transition: applied → interview
4. Implement add_note(note)
•	The note must not be blank.
•	Strip leading and trailing whitespace.
•	Raise ValueError for a blank note.
•	Append a valid normalized note to notes.
job.add_note("  Recruiter replied  ")
# notes should contain: ["Recruiter replied"]
5. Implement get_summary()
Return a human-readable string containing the company, role, status, and number of notes.
OpenAI | AI Engineer | interview | Notes: 2
You may choose the exact formatting, but it must remain clear and consistent.
6. State Ownership Requirement
Every JobApplication instance must own an independent notes list.
job1 = JobApplication("OpenAI", "AI Engineer")
job2 = JobApplication("Anthropic", "Backend Engineer")

job1.add_note("Applied through website")

# job1.notes should contain the note
# job2.notes must still be []
Design checkpoint
Choose the dataclass mechanism that creates a fresh mutable list for each instance. Be able to explain why a plain mutable default is unsafe.
7. Equality Experiment
Use this experiment to inspect generated dataclass equality behavior. Do not change the design before observing the result.
job1 = JobApplication("OpenAI", "AI Engineer")
job2 = JobApplication("OpenAI", "AI Engineer")

print(job1 == job2)

job1.add_note("Applied online")
print(job1 == job2)
Before running the code, write down your prediction. Then explain whether notes participates in generated equality and why.

10. Restrictions
•	Do not manually define __init__.
•	Do not manually define __repr__.
•	Do not manually define __eq__.
•	Do not use frozen=True for this model; status and notes are intentionally mutable.
•	Do not use Pydantic, JSON persistence, SQLite/PostgreSQL, APIs, or external frameworks in this task.
The purpose is to understand dataclass-generated behavior and design a small domain object with explicit invariants and controlled mutations.
